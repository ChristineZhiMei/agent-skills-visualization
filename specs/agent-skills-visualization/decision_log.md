# 决策日志：Agent Skills Visualization

记录设计中的关键决策与理由，便于团队阅读与后续变更追溯。

---

## D1. 功能名称与 specs 目录

- **决策**：功能展示名称使用 `Agent Skills Visualization`，仓库名与 specs 目录沿用 `agent-skills-visualization`（`specs/agent-skills-visualization`）。
- **理由**：满足产品层面需要人类可读名称，同时保持仓库名与目录结构稳定、便于脚本与历史记录延续。

---

## D2. 需求文档来源

- **决策**：在尚无正式需求技能产出的前提下，基于「当前项目结构」与「用户对话（项目启动方式）」归纳出 `requirements.md`，并注明可后续用需求技能细化。
- **理由**：满足设计文档须基于需求文档的约束，同时响应用户「根据和我的对话来补充」的诉求，避免阻塞创建设计文档。

---

## D3. 架构：沿用 Electron 三进程 + electron-vite

- **决策**：不改变现有主进程 / 预加载 / 渲染进程划分，构建与入口完全沿用 electron-vite 约定（main、preload、renderer 三块配置）。
- **理由**：项目已按 electron-vite 标准搭建，设计与现有实现一致，降低理解与维护成本；参考 [electron-vite 文档](https://electron-vite.org/)。

---

## D4. 预加载：使用 @electron-toolkit/preload 并预留 api

- **决策**：通过 `contextBridge` 暴露 `electronAPI`（@electron-toolkit/preload）与自定义空对象 `api`；在非 contextIsolated 环境下回退到挂载到 window。
- **理由**：与现有代码一致；预留 `api` 便于后续扩展自定义暴露方法，且类型已在 `preload/index.d.ts` 中声明。

---

## D5. 错误处理粒度

- **决策**：预加载仅对 contextBridge 做 try/catch 并 console.error；主进程与渲染进程不新增复杂错误码或统一错误页，以「不崩溃、可排查」为主。
- **理由**：当前需求未要求用户可见的错误提示或统一错误协议，保持与现有实现一致，避免过度设计。

---

## D6. 测试策略：以手动验证为主，PBT 不引入

- **决策**：验收标准当前通过文档与手动验证满足；建议后续可加 Vitest 单元测试与 E2E（如 Playwright for Electron）；不引入基于属性的测试（PBT）。
- **理由**：需求为启动、构建与简单 IPC，无解析/序列化/复杂数据结构，PBT 收益有限；技能要求仅在存在合适场景时考虑 PBT。

---

## D7. 文档与启动说明

- **决策**：将「如何启动」明确写入设计文档（架构、组件与接口、脚本），并依赖 README 作为对用户的启动说明；需求中 REQ-4 / AC-5 对应文档与可发现性。
- **理由**：用户对话中关心「这个项目怎么启动」，设计文档与需求均需体现安装、开发、构建的完整路径，并与 README 保持一致。

---

## D8. 力模拟与渲染方案（技能图谱）

- **决策**：使用 **d3-force** + 自定义 Vue 组件：节点用 **div**（技能节点圆角矩形、目录节点圆形），边用 **SVG**，连接点均为节点几何中心；以满足「圆角矩形/圆形、连接点中心、div 可填充内容」。
- **理由**：现成 Vue 图库多偏 SVG 节点，难以满足「div 可填充内容」与「连接点正中心」；d3-force 与 Vue 响应式结合简单，拖拽通过 `fx/fy` 与 `simulation.restart()` 即可实现。

---

## D9. 先模拟数据、脚本解析预留

- **决策**：先实现基于 **模拟数据** 的关系图谱示例，不依赖真实目录；脚本解析 skills 目录作为后续迭代，主进程通过 IPC 暴露「解析结果」接口预留。
- **理由**：需求明确「先创建一个关系图谱的示例，使用模拟数据」；先打通力导向与渲染，再接入主进程扫描与解析，降低首版复杂度。

---

*以上决策在创建设计文档时确定；若后续需求或实现变更，可在此追加或修改条目。*
